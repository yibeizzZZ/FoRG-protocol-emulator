# Project Milestones

This document defines the development roadmap for the FoRG Protocol Emulator ASIC project.

The goal is not only to build a working protocol emulator, but to develop a compact, programmable architecture with a clear technical contribution beyond simply reproducing existing programmable I/O designs.

The project targets the Jane Street Protocol Emulator ASIC Competition.

---

# Phase 0 — Infrastructure and Baseline

## Milestone 0 — Repository and Toolchain Setup

**Target: Week 1**

Goal: establish a reproducible development environment immediately.

Tasks:

* ✅Initialize the repository from the Tiny Tapeout IHP Verilog template
* ✅Verify RTL simulation locally
* Verify CI through GitHub Actions
* Verify synthesis completes successfully
* Configure the target Tiny Tapeout tile allocation
* Establish repository structure
* Establish pull request and issue conventions
* Add basic development documentation

Repository structure should include:

```text
src/
test/
firmware/
docs/
scripts/
```

Deliverables:

* Passing default simulation
* Passing CI
* Successful first synthesis
* Documented local development workflow

This milestone should be completed quickly. Infrastructure work must not delay architectural exploration.

---

## Milestone 1 — Minimal Fixed UART Baseline

**Target: Week 1**

Goal: obtain a working hardware timing reference before introducing programmability.

Tasks:

* Implement a minimal UART transmitter in RTL
* Transmit an 8-bit value
* Support configurable bit timing
* Add cocotb verification
* Verify start bit, data bits, and stop bit timing
* Measure synthesis area and timing

Required test values:

* `0x00`
* `0x55`
* `0xAA`
* `0xFF`

Deliverables:

* Correct UART waveform in simulation
* Automated UART test
* Initial area report
* Initial timing report

The fixed UART implementation is only a reference baseline and should not become part of the final architecture.

# Phase 1 — Programmable Core

## Milestone 2 — Minimal Programmable Protocol Engine

**Target: Week 2**

Goal: replace fixed protocol logic with a programmable execution engine as early as possible.

Minimum hardware components:

* Program counter
* Instruction memory
* Instruction decoder
* Small register file
* GPIO read/write path
* Delay or cycle-count mechanism
* Conditional branch support

Initial candidate instructions may include:

```text
SET
READ
MOV
WAIT
JMP
JNZ
SHIFT
```

The ISA is intentionally temporary.

Tasks:

* Define a first-pass instruction format
* Implement instruction fetch and decode
* Execute basic GPIO operations
* Execute deterministic WAIT behavior
* Execute basic branches
* Add instruction-level cocotb tests
* Measure area after every major architectural feature

Deliverables:

* Executable firmware program
* Deterministic GPIO waveform generated by firmware
* First ISA specification
* First programmable-core synthesis report

The goal is speed of iteration, not architectural elegance.

---

## Milestone 3 — UART Implemented as Firmware

**Target: End of Week 2**

Goal: prove that a real protocol can run entirely on the programmable engine.

Tasks:

* Implement UART TX using firmware
* Remove dependence on dedicated UART logic
* Support configurable timing
* Verify multiple bytes
* Compare results against the fixed UART baseline
* Measure:

  * instruction count
  * cycles per transmitted bit
  * area
  * maximum clock frequency

Questions to answer:

* Which instructions are used most frequently?
* Which operations require too many instructions?
* Which architectural limitations appear immediately?
* Which features appear unnecessary?

Deliverables:

* Firmware-based UART TX
* Comparison against the fixed UART baseline
* Short architectural limitations report

At this point, the team should stop adding features blindly and begin exploring architectural alternatives.

# Phase 2 — Architecture Exploration

## Milestone 4 — Architecture Exploration Sprint

**Target: Weeks 3–4**

Goal: intentionally explore competing architectural directions before committing to the final design.

At least **three meaningful architecture ideas** should be investigated.

Possible directions include:

* Multi-state-machine architecture
* Shared execution engine with multiple protocol contexts
* Event-driven execution
* Compact instruction encoding
* Pin-pattern output instructions
* Parallel GPIO updates
* Hardware-assisted shifting
* Hardware-assisted timing
* Specialized delay/event counters
* Small protocol-oriented FIFO
* Zero-overhead loops
* Deterministic multi-engine synchronization
* Program compression
* Microcoded execution
* Protocol-specific coprocessor primitives
* Formal-verification-friendly architecture

Each proposed idea should be evaluated according to:

* Area cost
* Timing cost
* Firmware complexity
* Protocol expressiveness
* Verification complexity
* Scalability
* Novelty
* Ease of implementation

Each idea must have at least one concrete experiment.

Example:

```text
Idea:
Parallel pin update instruction

Experiment:
Implement SPI using SET instructions vs parallel OUT instruction

Measure:
- instruction count
- cycles per bit
- area overhead
```

Deliverables:

* At least three architecture experiments
* Quantitative comparison table
* Architecture exploration document
* At least one prototype that differs meaningfully from the initial minimal engine

This is a core milestone, not optional exploratory work.

---

## Milestone 5 — RP2040 PIO / Existing Design Comparison

**Target: Week 4**

Goal: understand existing solutions well enough to clearly define the project's contribution.

Study at minimum:

* RP2040 PIO
* TI PRU
* Relevant programmable protocol engines or I/O processors

Compare:

* Instruction set
* State machine model
* GPIO model
* Timing model
* Memory model
* Synchronization model
* FIFO support
* Number of concurrent engines
* Area-oriented design decisions

The team must answer:

1. What problem do existing programmable I/O architectures solve well?
2. Where are they inefficient or inflexible?
3. Which limitation are we targeting?
4. Why is that limitation relevant to protocol emulation?
5. What measurable advantage could our architecture provide?

Deliverable:

`docs/architecture_comparison.md`

This document should directly motivate the final architecture.

# Phase 3 — Novelty Selection and Architecture Freeze

## Milestone 6 — Novelty Review

**Target: Beginning of Week 5**

Goal: identify the technical contribution that makes the project more than a reproduction of existing designs.

The team must identify at least one primary contribution.

Possible contribution categories:

### Architecture

Examples:

* Better multi-protocol concurrency
* Lower-area programmable engine
* More deterministic timing
* More efficient GPIO operations
* Better synchronization
* More compact firmware
* Better handling of protocol events

### Verification

Examples:

* Formal-first architecture
* Automatically generated protocol verification
* Differential verification against software reference models
* AI-assisted test generation
* Program-level safety verification

### Tooling

Examples:

* Protocol DSL
* Compiler from protocol specification to firmware
* Automatic cycle scheduling
* Automatic timing verification
* Automatic firmware optimization

The novelty must be:

* clearly defined
* experimentally measurable
* realistically implementable
* relevant to protocol emulation

Deliverable:

`docs/novelty.md`

The document must contain:

```text
Problem
Existing approach
Our approach
Expected advantage
Cost
Experiment used to validate it
```

No architecture freeze should happen before this review.

## Milestone 7 — Architecture Freeze

**Target: End of Week 5**

Goal: select the architecture that will be carried to tapeout.

Finalize:

* Instruction width
* Instruction encoding
* Register count
* GPIO count
* Program memory organization
* Timer design
* Branch model
* Shift operations
* FIFO design
* Number of execution engines
* Synchronization behavior
* Firmware loading mechanism
* Reset behavior
* Host interface

Produce diagrams for:

* datapath
* control path
* instruction format
* memory organization
* GPIO path

Tasks:

* Remove experimental features that do not justify their area
* Run full synthesis
* Estimate final area margin
* Estimate timing margin
* Document architectural tradeoffs

Deliverables:

* Frozen ISA
* Frozen microarchitecture
* Block diagram
* Synthesis results
* Architecture specification

After this milestone, ISA changes should require a documented reason.

# Phase 4 — Protocol Stress Testing

## Milestone 8 — SPI

**Target: Week 6**

Goal: stress the architecture with synchronous full-duplex communication.

Tasks:

* Implement SPI master
* Support MOSI
* Support MISO
* Support SCLK
* Support chip select
* Support multiple bytes
* Test at multiple clock divisors
* Verify data sampling timing

Measure:

* instructions per transferred bit
* maximum achievable SPI frequency
* firmware size
* engine utilization

Deliverables:

* Working SPI firmware
* Automated SPI tests
* Performance report

---

## Milestone 9 — I2C

**Target: Week 7**

Goal: test bidirectional pins, branching, protocol events, and irregular timing.

Tasks:

* START
* STOP
* address transfer
* write
* read
* ACK
* NACK
* repeated START
* bidirectional SDA
* clock stretching if architecture permits

Measure:

* firmware size
* branch overhead
* timing flexibility
* architecture limitations

Deliverables:

* Working I2C firmware
* Automated I2C model
* I2C compliance tests

By the end of this milestone, UART, SPI, and I2C must all run on the same programmable architecture.

# Phase 5 — Verification

## Milestone 10 — Automated Verification Framework

**Target: Weeks 7–8**

Goal: make verification a first-class part of the design rather than a final-stage task.

Required verification layers:

### Directed Testing

* instruction tests
* reset tests
* UART tests
* SPI tests
* I2C tests

### Randomized Testing

Randomize:

* payloads
* clock divisors
* firmware sequences
* delays
* protocol traffic

### Differential Testing

Compare RTL behavior against:

* Python reference models
* protocol decoders
* known-good behavioral models

### Assertions

Examples:

* valid program counter range
* legal state transitions
* FIFO correctness
* reset correctness
* legal GPIO behavior

Deliverables:

* Regression suite
* Automated randomized tests
* Continuous integration
* Verification coverage report

---

## Milestone 11 — Formal Verification

**Target: Weeks 8–9**

Goal: formally prove critical architectural properties.

Candidate properties:

* no illegal PC state
* bounded WAIT completion
* reset correctness
* FIFO safety
* deterministic instruction execution
* legal output-enable behavior
* valid synchronization
* no impossible internal state

Tasks:

* Select a formal tool
* Build formal harness
* Verify at least three meaningful properties
* Document counterexamples and fixes

Deliverable:

`docs/formal_verification.md`

Formal verification should support the project's technical contribution, not exist only as a checkbox.

# Phase 6 — FPGA Validation

## Milestone 12 — FPGA Prototype

**Target: Weeks 9–10**

Goal: test the emulator against physical devices before ASIC tapeout.

Tasks:

* Port RTL to FPGA
* Run UART against a host computer
* Run SPI against a peripheral
* Run I2C against a real device
* Capture signals with a logic analyzer
* Compare physical timing against simulation

Optional:

* Run multiple protocol engines simultaneously
* Stress maximum protocol rate
* Test long-running firmware

Deliverables:

* FPGA demonstration
* Captured waveforms
* Hardware validation report

# Phase 7 — ASIC Optimization

## Milestone 13 — Area Optimization

**Target: Weeks 10–11**

Goal: aggressively reduce unnecessary hardware while preserving the project's contribution.

Review:

* register file
* instruction decoder
* counters
* FIFOs
* program memory
* GPIO control
* synchronization logic

Tasks:

* Identify largest cells
* Compare architectural alternatives
* Remove unused paths
* Reduce unnecessary widths
* Evaluate SRAM vs registers where appropriate
* Record optimization impact

Deliverable:

Before/after area comparison.

---

## Milestone 14 — Timing Closure

**Target: Weeks 11–12**

Goal: ensure the implementation meets physical timing constraints.

Tasks:

* Run place and route
* Inspect critical paths
* Fix timing violations
* Reduce fanout
* simplify long decode paths
* pipeline only if necessary
* verify protocol timing after optimization

Deliverables:

* Passing timing report
* Stable post-layout simulation if available

---

# Phase 8 — Demonstrating Novelty

## Milestone 15 — Stretch Protocol or Architecture Demonstration

**Target: Weeks 12–13**

Goal: demonstrate a capability that clearly benefits from the chosen architecture.

Possible targets:

* JTAG
* SWD
* PS/2
* CAN
* low-speed USB
* 10 Mbit Ethernet
* custom protocol

The protocol should be selected based on what best demonstrates the architecture's unique strength.

Example:

If the contribution is multi-engine synchronization, select a protocol or workload that demonstrates simultaneous timing-sensitive channels.

If the contribution is compact firmware, compare firmware size against an RP2040-PIO-style implementation.

Deliverables:

* Working demonstration
* Comparison against baseline
* Quantitative evidence supporting the project's novelty claim

# Phase 9 — Final Evaluation

## Milestone 16 — Architecture Benchmarking

**Target: Week 13**

Goal: produce quantitative evidence supporting the design.

Benchmarks should include:

* area
* clock frequency
* UART throughput
* SPI throughput
* firmware size
* cycles per protocol bit
* GPIO timing precision
* concurrent protocol capability
* power estimate if practical

Compare where possible against:

* initial architecture
* fixed protocol implementation
* RP2040 PIO-style behavior
* alternative design explored earlier

Deliverable:

`docs/results.md`

The final project should be able to defend architectural choices with measurements rather than intuition.
